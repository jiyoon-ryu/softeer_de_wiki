## 1. 오늘 활동

- **한 일:** 팀 프로젝트 **“Road Comfort API”**의 전체 데이터 아키텍처를 구체화하고, TLC Zone별 특성을 활용하기 위한 `zone_scores` 생성 로직을 구현했다.
- 차량 센서 데이터가 **수집 → Kafka → Spark 처리 → 저장 → API 제공**으로 이어지는 흐름을 아키텍처로 정리하고, Airflow·Grafana·Prometheus 등 운영 요소의 역할도 함께 구체화했다.
- Spark의 처리 구조와 분산 연산 방식을 다시 학습하면서 프로젝트에서 Spark가 어떤 데이터를 어떤 단계에서 처리할지 정리했다.

## 2. Keep

- **아키텍처를 실제 데이터 흐름 기준으로 구체화한 것.** 단순히 기술을 나열하는 것이 아니라 데이터가 어디서 생성되고, 어떻게 처리·저장되고, 최종적으로 어떻게 활용되는지를 기준으로 구조를 잡았다.
  - **Action:** 이후 아키텍처 설계에서도 기술 선택보다 데이터 흐름과 각 컴포넌트의 역할을 먼저 정의한다.
- **Zone 특성을 단순 Feature에서 실제 활용 가능한 Score로 변환한 것.** Percentile 기반 정규화와 Tag 규칙을 통해 지역 특성을 비교 가능한 형태로 만들었다.
  - **Action:** 파생 지표를 만들 때 계산 기준과 가중치, 예외 처리 기준을 함께 명시한다.

## 3. Problem

- **초기에는 아키텍처에 여러 기술이 포함되면서 각 기술이 꼭 필요한지 구분하기 어려웠다.**
- `zone_scores`를 만드는 과정에서도 고정 임계값이나 규칙 순서에 따라 결과가 달라질 수 있는 문제가 있었다.
  - **개선 Action:** 각 기술은 실제 역할이 있는 경우에만 남기고, Score와 Tag는 가능한 한 상대적 기준과 데이터 기반 규칙을 사용하도록 수정한다.

## 4. Try

- Spark에서 **센서 데이터의 정제·집계·세그먼트별 Comfort Score 계산**이 실제로 어떻게 수행될지 처리 로직을 구체화한다.
- Kafka → Spark → 저장소로 이어지는 데이터 흐름을 직접 구현해 아키텍처와 실제 코드가 일치하는지 확인한다.
- TLC OD 수요와 Zone Score를 결합하여 **센서 수집 우선순위가 높은 OD를 선정**하고 이후 실제 도로 Segment 수집 범위로 연결한다.
