## 1. 오늘 활동

- **한 일:** 팀 프로젝트 **“Road Comfort API”**의 데이터 흐름과 Silver 계층 스키마를 구체화했다.
- `sensor_event → processed_sensor_event → hourly_segment_features → hourly_comfort_score → segment_comfort_score`로 처리 단계를 나누고, Feature 계산과 Comfort Score 계산을 분리했다.
- 승차감 계산에 필요한 RMS, P95, 급가속·급제동, 조향 전환, Steering Rate 등의 역할을 정리하고 `steering_angle`을 시뮬레이터에 추가하기 위한 이슈도 정의했다.
- Kafka와 Iceberg가 실제 요구사항에 필요한지 검토하고, LION 기반 `road_segment` 생성 작업의 범위도 정리했다.

## 2. Keep

- **중간 Feature와 최종 Score를 분리한 것.** `hourly_segment_features`에 RMS·P95·이벤트 횟수 등을 저장하고, 이를 이용해 `hourly_comfort_score`를 계산하도록 나눠 Score 공식이 변경되어도 Feature를 재사용할 수 있게 했다.
  - **Action:** 이후에도 계산 재료와 최종 결과를 분리해 재처리와 버전 변경에 유리한 구조로 설계한다.

- **기술을 사용하는 이유를 프로젝트 요구사항과 연결해서 검토한 것.** Kafka는 실시간 점수 제공보다는 지속적으로 발생하는 센서 이벤트의 안정적인 수집·버퍼링에, Iceberg는 Silver 데이터의 재처리와 스키마 변경에 의미가 있음을 정리했다.
  - **Action:** 새로운 기술을 추가할 때 기능보다 먼저 실제로 해결하는 문제를 명확히 한다.

## 3. Problem

- **처음에는 하나의 Silver 테이블에 Feature와 Score가 섞여 있어 각 데이터의 역할과 Grain이 불명확했다.**
- 속도 구간, 차량 수, Steering Rate 등 필요한 Feature를 모두 넣으려다 스키마가 불필요하게 복잡해질 가능성이 있었다.
  - **개선 Action:** 최종 활용 목적에 직접 필요한 데이터만 남기고, `1시간 × Segment × Vehicle Profile`처럼 각 테이블의 Grain을 먼저 고정한 뒤 컬럼을 결정한다.

## 4. Try

- LION 원본 데이터를 분석하여 **`road_segment` 스키마와 변환 규칙을 확정하고 실제 Spark Transform을 구현한다.**
- `processed_sensor_event → hourly_segment_features` 단계에서 Map Matching과 RMS·P95·급가속/급제동·조향 Feature 집계 로직을 구체화한다.
- 로컬 환경에서 먼저 Bronze → Silver 처리와 재처리를 검증한 뒤 S3/Iceberg 및 Airflow 환경으로 확장한다.
