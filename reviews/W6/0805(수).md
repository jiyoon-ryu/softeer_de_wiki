## 1. 오늘 활동

- **한 일**: Airflow + MySQL 기반 "서울시 따릉이 이용정보 ETL 파이프라인" 구축 완료.
  Docker 환경 세팅 → API 수집 함수 개발 → 정제/집계/적재 로직 구현 → Airflow DAG 연결 → 실행 성공 및 멱등성 검증까지 전 과정 완주.

## 2. Keep

- **로직을 Airflow에 넣기 전에 순수 Python으로 먼저 검증한 것.**
  extract/transform/aggregate/load 각 함수를 독립적으로 테스트(샘플 데이터, 통합 스크립트)한 뒤 DAG에 옮겨서, 문제 생겼을 때 Airflow 문제인지 로직 문제인지 구분이 쉬웠다.
  - Action: 다음 프로젝트에서도 오케스트레이션 도구에 올리기 전에 핵심 로직은 항상 로컬에서 단위 테스트 먼저 통과시킨다.

- **멱등성을 "구현"에서 끝내지 않고 "실제로 두 번 실행해서" 검증한 것.**
  delete-then-insert 로직을 짜는 데서 그치지 않고, DAG를 두 번 트리거해서 같은 2,738건이 유지되는지 눈으로 확인했다.
  - Action: 멱등성/재실행 안전성이 요구되는 작업은 항상 "1회 실행 → 결과 확인 → 재실행 → 결과 비교"까지를 완료 기준으로 삼는다.

## 3. Problem

- **API 서버 오류(ERROR-500)를 코드/네트워크 문제로만 의심하다 오래 헤맸다.**
  실제 원인은 서비스명 오타`cycleRentUseDayInfo` vs `tbCycleRentUseDayInfo`였는데, 재시도 로직·페이지 크기·서버 상태만 계속 의심하며 시간을 썼다.
  - 개선 Action: API가 계속 실패하면 코드/네트워크를 의심하기 전에 **"성공 사례(팀원 코드, 공식 예시)와 요청 URL을 한 글자씩 비교"**하는 것을 먼저 한다.

- **문서(데이터셋 페이지) 텍스트만 보고 "서비스 종료"라고 성급하게 결론 내렸다.**
  숨겨진 템플릿 문구를 실제 서비스 상태로 오인해 잘못된 정보를 전달했다.
  - 개선 Action: 웹 페이지에서 상충되는 안내문(예: "종료" + "URL 오류"가 동시에 존재)이 보이면, 실제 렌더링 여부를 의심하고 다른 경로(직접 API 호출, 팀원 확인)로 교차 검증한 뒤 결론 내린다.

## 4. Try (새 시도)

- **API 연동 작업 시작 전에 "성공한 호출 예시 1개 확보"를 선행 단계로 고정.**
  이번처럼 서비스명/파라미터 형식이 헷갈리는 API는, 문서만 보고 짜지 말고 동료의 성공 사례나 공식 샘플 URL을 먼저 확보한 뒤 그걸 기준으로 코드를 짠다.

- **에러 원인 분석 시 "내 코드 vs 외부 요인" 이분법 전에 짧은 비교 체크리스트 사용.**
  실패한 요청과 성공한 요청(과거 것이든 팀원 것이든)을 문자열 단위로 diff 떠서 어디가 다른지부터 확인하는 습관을 다음 디버깅부터 시도해본다.
