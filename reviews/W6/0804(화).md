## 1. 오늘 활동

- **한 일**: 팀 프로젝트 **Road Comfort API**의 전체 아키텍처를 구체화했다.
- `dim_segment`, `enriched_segment_reference`, `od_segment_sequence`의 역할과 생성 과정을 정리했다.
- LION 도로 데이터와 TLC Taxi Zone 경계 데이터를 실제로 공간조인해 `dim_segment`와 지도 결과를 생성했다.
- 현대자동차 현직자에게 질문할 기술·도메인 관련 내용을 정리했다.

## 2. Keep

- **주요 데이터의 역할을 명확히 구분한 것.**  
  `dim_segment`는 도로 기준정보, `enriched_segment_reference`는 노면·방지턱 정보가 추가된 데이터, `od_segment_sequence`는 경로별 도로 구간 순서로 정의했다.

- **설계에 그치지 않고 실제 데이터로 검증한 것.**  
  LION 도로와 Taxi Zone을 직접 공간조인해 약 13만 개의 도로 구간에 Zone 정보를 매칭하고, 지도에서 결과를 확인했다.

- **현직자 질문을 기술뿐 아니라 자동차 도메인까지 확장한 것.**  
  실제 승차감 측정 방식, 차량별 편차, 도로 구간 단위, Comfort Score 검증 방법 등을 질문으로 정리했다.

- **Action**: 이후에도 주요 테이블의 생성 원천, 역할, 갱신 주기, 사용 위치를 먼저 정의한다.

## 3. Problem

- **1시간 단위 집계와 월간 Comfort Score 계산 과정이 문서에서 명확하게 구분되지 않았다.**  
  실제 의도는 센서 데이터를 1시간 단위로 중간 집계하고, 한 달치 결과를 모아 최종 Comfort Score를 계산하는 것이다.

- **시뮬레이션 데이터 생성과 점수 검증 사이에 순환 구조가 있었다.**  
  노면등급과 방지턱으로 센서값을 만들고, 다시 같은 정보를 점수 계산에 사용하면 결과가 미리 정해진 검증이 될 수 있다.

- **개선 Action**: `원본 센서 → 1시간 집계 → 월간 재집계 → Comfort Score` 흐름을 문서에 명확하게 작성한다. 또한 파이프라인 동작 검증과 실제 승차감 모델 검증을 구분한다.

## 4. Try

- **주요 테이블 정의표 작성**  
  각 테이블의 PK, 입력 데이터, 갱신 주기, 주요 컬럼, 사용 목적을 한 표로 정리한다.

- **현직자 피드백 반영표 작성**  
  답변을 `현재 설계 / 현업 의견 / 반영 여부 / 반영 이유`로 정리해 최종 아키텍처의 근거로 남긴다.

- **검증 목적 분리**  
  공간조인 정확도, 데이터 누락 여부, 점수 계산 정상 여부, 실제 승객 체감과의 일치 여부를 별도의 검증 항목으로 관리한다.
