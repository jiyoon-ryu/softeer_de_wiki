## 1. 오늘 활동

- **한 일:** 팀 프로젝트 **“Road Comfort API”**의 문제 정의를 최종적으로 정리하고, 이를 구현하기 위한 AWS 인프라 자원까지 구체화했다.
- 최종 문제 정의는 다음과 같이 확정했다.
  - **누구의 문제?** 현대자동차의 내비게이션 경로 추천 시스템 개발자
  - **어떤 문제?** 경로 알고리즘 개발 시 필요한 **세그먼트별 승차감을 나타내는 표준 데이터셋이 없다.**
  - **Index:** 승차감 반영 경로의 **선택률 및 만족도**
- 시스템 구현을 위해 EC2 3대, EMR, S3를 사용하는 AWS 아키텍처를 검토하고 각 리소스의 역할과 규모를 정했다.

## 2. Keep

- **문제의 주체와 해결하려는 문제를 같은 층위로 맞춘 것.**  
  기존에는 데이터 엔지니어, 승객, 내비게이션 서비스의 문제가 혼재되어 있었지만, 최종적으로 **“경로 추천 시스템 개발자가 사용할 승차감 표준 데이터가 없다”**는 문제로 범위를 명확히 했다.
  - **Action:** 다음 프로젝트에서도 `누가 → 무엇을 못 하고 있는가`가 한 문장으로 연결되는지 먼저 확인한다.

- **Comfort Score 자체를 문제나 성과로 정의하지 않은 것.**  
  Comfort Score는 경로 추천 알고리즘이 승차감을 비교하기 위해 사용하는 데이터이며, 실제 효과는 이를 활용한 경로의 선택률과 만족도로 검증하도록 구분했다.
  - **Action:** 데이터 산출물과 실제 서비스 성과지표를 분리해서 정의한다.

- **문제 정의 이후 실제 인프라까지 연결한 것.**  
  단순 아이디어에 그치지 않고 데이터 규모와 처리 방식을 고려해 AWS 리소스 구성까지 구체화했다.
  - **Action:** 이후에도 문제 → 데이터 → 파이프라인 → 인프라가 자연스럽게 연결되는지 함께 검토한다.

## 3. Problem

- **피드백 과정에서 ‘필요한 이유’와 ‘풀어야 하는 문제’를 반복해서 혼동했다.**  
  “Comfort Score가 필요하다”, “승객이 편안한 경로를 선택할 수 있다”는 설명은 배경이나 기대효과에 가까웠고, 실제 문제 정의가 아니었다.

- **초기 Index가 프로젝트 구현 범위와 맞지 않았다.**  
  API와 데이터셋을 만드는 프로젝트에서 `고충격 구간 노출시간 30분 → 10분`처럼 실제 차량 주행 결과를 직접 Index로 잡으면서 문제 정의와 성과지표가 따로 놀았다.
  - **개선 Action:** 현재는 상위 서비스에서 검증 가능한 **승차감 반영 경로의 선택률 및 만족도**를 성과지표로 두고, 프로토타입 단계에서는 이를 검증할 수 있는 데이터를 함께 설계한다.

## 4. Try

- **AWS 아키텍처를 실제 데이터 규모에 맞춰 검증한다.**
  - EC2 3대: `m6g.xlarge`, `r6g.large`, `t4g.medium`
  - EMR: Spark Batch Job 처리
  - S3: 원천·가공 데이터 적재, 약 `1억 건/day` 규모 가정
- 각 리소스에 대해 단순히 사용한다에서 끝내지 않고 **왜 해당 인스턴스 타입과 서비스를 선택했는지 비용·성능 근거를 정리한다.**

- **문제 정의와 프로토타입 결과를 다시 연결한다.**  
  세그먼트별 Comfort Score 데이터셋이 실제로 경로 추천 알고리즘에서 활용 가능한 형태인지 확인하고, 후보 경로 간 승차감 차이를 비교할 수 있는 예시를 만든다.

- **Index 측정 방법을 구체화한다.**  
  `승차감 반영 경로 선택률`과 `만족도`를 어떤 실험 또는 사용자 평가로 측정할 것인지 정의하고, 실제 검증이 어려운 부분은 프로젝트의 기대효과와 직접 검증 지표를 구분해 작성한다.
