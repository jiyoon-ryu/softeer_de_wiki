## 2. Keep
- **인프라를 처음부터 다시 만들지 않고 재사용한 것.** W4M1에서 만든 Dockerfile/docker-compose.yml/submit.sh 구조를 그대로 활용해서, 이번 과제는 분석 로직 작성에만 집중할 수 있었다.
  - Action: 다음 과제에서도 시작 전에 **이전 과제 산출물 중 재사용 가능한 게 있는지 먼저 확인**
- **코드를 여러 버전으로 비교하며 개선한 것.** DataFrame reader를 거치는 방식 → 순수 `sc.textFile()` 파싱 방식으로, 안전성(콤마 포함 필드, 날짜 타입 에러 위험)과 성능(Job 수 절감, 셔플 스테이지 절감)을 단계적으로 개선했다.
  - Action: 코드를 한 번에 끝내지 말고 **"동작 → 안전성 점검 → 성능 최적화" 순서로 리팩토링하는 습관** 유지

## 3. Problem
- **디버깅용 `count()` 호출을 지우지 않은 채로 DAG를 캡처했다.** 그 결과 Stage 번호가 두 자릿수로 찍히고, 앞쪽 Stage가 "skipped"로 표시돼서 처음엔 "이게 맞나?" 헷갈렸다.
  - 개선 Action: **최종 캡처 전에는 디버깅 코드를 반드시 제거하고 깨끗한 상태로 한 번 더 실행**한다.
- **"리포트에 뭘 넣어야 하나"를 스크린샷 개수 문제로 오해했다.** 요구사항이 "리포트 안에 스크린샷 포함"인데, 처음엔 "스크린샷 자체가 제출물"인 것처럼 접근했다.
  - 개선 Action: 요구사항 문장을 읽을 때 **"무엇을 제출하라는 건지" 주어와 목적어를 먼저 분리**해서 확인한다.

## 4. Try (새 시도)
- **"메인 코드 1회 실행 → 깨끗한 DAG 캡처 → 리포트 작성" 순서로 마무리 실험.** 디버깅 흔적 없는 최종 실행 결과 하나로 전체 스토리(전체 실행 Job 1장 + 필요시 캐싱 비교 1장)를 구성해본다.
  - 이번엔 중간 점검용 코드가 최종 산출물에 섞여 들어갔는지 확인
- **리포트 구조 체크리스트 적용.** 데이터셋 정보 / 클러스터 구조 / transformation 5개 위치 / 집계 결과 로그 / DAG 해석 / 성능 최적화 포인트, 이 6개 항목을 표로 만들어 각 항목이 채워졌는지 예/아니오로 표시하고 시작한다(항목 누락 방지).
